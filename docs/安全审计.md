# 安全审计报告

审计日期：2026-11-03
审计范围：`console/` `core/` `tools/` `theme/` `install.sh` `deploy.sh`
方法：静态代码审查 + 动态验证（实际构造攻击载荷打线上服务）

---

## 一、结论

发现 **4 项高危**、**9 项中危**、**6 项低危**。高危项已全部修复并复测通过。

核心判断：系统**没有**教科书级的严重漏洞（无命令注入、无 SQL 注入、无 webshell 上传、无开放递归 DNS）。
但存在**一条完整的接管链**：未转义的用户内容 → 公开分享页 → 同源脚本执行 → 以登录员工身份调用控制台 API。

## 二、高危项（已修复）

### H1 公开分享页存储型 XSS

**位置**：`core/kf_sections.py` 渲染层、`console/kf_console.py:3548`

**成因**：区块渲染器（`hx`/`pp`/`btn`/`ul`/`img_tag`）直接拼接用户文本，零转义；
`/s/<token>` 分享页在 `_guard()` 鉴权**之前**返回，任何拿到链接的人都能拿到未转义 HTML。

**危害**：分享链接本就要发给客户预览。客户打开即在**控制台同源**下执行脚本，
可借员工已登录的会话调用 `/api/users`、`/api/dns/*`、`/api/ledger` 等接口——
等于把客户预览链接变成控制台接管入口。

**验证**（修复前）：
```
1) 创建分享链接: 200 649kPpCuqdc8
2) 未认证访问 /s/649kPpCu -> HTTP 200
3) 载荷是否原样出现在 HTML: 成立 ✗ 存储型 XSS
   回显: <script>window.__XSS__=1;document.title="pwned"</script>Hello</h1>
```

**修复**：渲染层统一 `html.escape`；URL 过 `safe_url()` 白名单（挡 `javascript:`/`data:`）；
`rich` 块走 `sanitize_rich()` 剔除 `<script>`/`on*=`/危险协议；分享页与预览页标题同样转义。

**复测**：`分享页含可执行 <script>: False`

---

### H2 `/api/state` 明文下发邮件 API Key

**位置**：`console/kf_console.py` `/api/state`

**成因**：`settings()` 把整个 `settings.json` 合并返回，其中 `smtp.api_key` 未脱敏。
`/api/smtp` 做了脱敏，但 `/api/state` 漏了。

**危害**：任何登录用户（含 ops/finance 角色）都能读到发信 API Key，
可直接用于发信（冒名、钓鱼、消耗额度）。

**验证**（修复前）：
```
角色: ops | me: alice
/api/state 里 settings.smtp = {"from": "", "api_key": "re_LEAK_TEST_12345", ...}
→ api_key 是否明文下发: 是 ✗ 泄露
```

**修复**：`/api/state` 下发前对 `smtp.api_key`、`smtp.pass` 做掩码。

**复测**：`/api/state 的 api_key: '' → 已脱敏 ✓`

---

### H3 容器编排文件权限过宽

**位置**：`tools/kf_provision.sh`

**成因**：`docker-compose.yml` 内含 `MARIADB_PASSWORD` 与 `MARIADB_ROOT_PASSWORD` 明文，
但生成后未 `chmod`（同脚本的 `wp.env`、`handover.md` 都做了 600，唯独 compose 漏了）。

**危害**：同主机其他用户可读取全部站点数据库口令。

**修复**：生成后立即 `chmod 600`。

---

### H4 交接单含数据库密码且对全部角色开放

**位置**：`tools/kf_provision.sh` 交接单模板、`console/kf_console.py` `handover_pdf`

**成因**：
- 交接单模板写入 `- 密码：$DBPASS`（数据库 root 口令）
- PDF 全文渲染该文件，`GET /api/site/<slug>/handover.pdf` 只过 `_guard()`，
  **不校验角色**——`can_write` 只作用于 POST

**危害**：finance 角色可导出含数据库口令的 PDF；而这张单子本来就是要发给客户的。

**修复**：交接单不再包含数据库密码；PDF 导出限制为 admin/ops。

**复测**：`finance 角色导出交接单: 403 → 已拦截 ✓`

## 五、明确安全的部分

- **无命令注入**：全部 `subprocess` 为 list 形式，无 `shell=True`，无用户输入拼进 shell 字符串
- **无 SQL 注入**：`kf_template.py` 全程走 WordPress API（`wp_insert_post`/`update_option`），无 SQL 拼接
- **无法上传 webshell**：服务端重命名 + 魔数白名单（JPEG/PNG/WebP/GIF）+ Pillow 重编码为 WebP，SVG 不在白名单
- **DNS 无开放递归**：只回答自己托管的区，其余 `REFUSED`
- **路径穿越已封堵**：所有 slug 走 `SLUG_RE`，所有静态文件读取有 `resolve()` + 前缀校验
- **密码存储**：PBKDF2-SHA256 / 120k 迭代 / 随机盐
- **MFA**：TOTP RFC 6238，恢复码一次性消费，改密码需验旧密码
- **登录防护**：账号级锁定（5 次/15 分钟）+ IP 级拦截 + 弱密码库
- **审计日志**：JSON Lines 格式，注入无法伪造行
- **容器**：端口只绑 `127.0.0.1`，无特权模式，无 `docker.sock` 挂载
- **密钥不落 stdout**：脚本日志不打印任何密码

### 当前架构

```
公网 :18444 (TLS)  →  nginx 用户态实例  →  127.0.0.1:18090 (后台)
                              ↓
                    X-Forwarded-For: $remote_addr
                    X-KF-Proxy-Secret: <共享密钥>
```

反代用 `$remote_addr` **覆盖**客户端自带的 `X-Forwarded-For`，
后台只有在校验到正确的 `X-KF-Proxy-Secret` 后才采信转发来的 IP。
直连后台时，转发头一律无效。

实测：
```
经反代（真密钥）:            {"ip": "127.0.0.1", "xff": "127.0.0.1", "proto": "https"}
直连 + 伪造 XFF + 假密钥:     {"ip": "127.0.0.1", "xff": "6.6.6.6"}   ← 伪造被忽略 ✓
直连 + 伪造 XFF + 真密钥:     {"ip": "6.6.6.6"}                        ← 有密钥才采信
```
